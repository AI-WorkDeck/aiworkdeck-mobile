## 发布顺序

1. 先部署 `https://case.aiworkdeck.com/client/` 客户门户及对应案件库后端。
2. 从完整 App 的项目列表进入尽调协作，输入合成项目的邀请码，真机验证拍照、文件上传、历史下载、
   补传和申诉。页面会话与 App 账户独立；入口目前限中国区账户。
3. iOS 可以先上传 1.7.0 到 TestFlight。保留正在审核的 1.6.2，不撤回、不改其文案、不替换构建。
   待 1.6.2 上架后，再创建 1.7.0 的 App Store 版本记录、挂载构建并按本轮发布安排提审。
4. Android CI 生成签名包后，核对版本和签名再交各渠道。CI 本身不上传 Google Play 或国内商店。
5. 小程序先确认 `case.aiworkdeck.com` 业务域名，上传体验版并真机验证；鸿蒙先补齐发布签名条件。

本功能不包含关闭 App 后的 APNs / 厂商推送，商店文案不得将站内提醒描述为离线系统推送。

## iOS 命令与边界

`.github/workflows/appstore-build.yml` 监听所有分支的 push，只有最新提交信息包含 `[appstore]`
才打包上传，没有 `workflow_dispatch`。建议发布提交标题：

```text
Release iOS 1.7.0 and Android 1.2.0 due diligence collaboration [appstore]
```

审阅通过后由主任务提交并推送；推送这个提交会直接开始上传：

```bash
git push origin HEAD
gh run list --repo AI-WorkDeck/aiworkdeck-mobile --workflow appstore-build --limit 5
```

CI 使用 `fastlane ios ci_appstore`，从 `ios/project.yml` 读取 1.7.0；构建号通过
`scripts/asc-next-build.py` 查询 builds 和 buildUploads 后分配，上传任务串行执行。
不要改 `CURRENT_PROJECT_VERSION: "1"`，它由归档参数覆盖。主 App、Live Activity、Watch
三份描述文件均须使用现有北京团队签名，不更换已备案证书。

1.6.2 上架后，使用总表登记的原位 ASC 环境，先只读核对，再执行新版本步骤：

```bash
.venv/bin/python scripts/asc-listing.py status
.venv/bin/python scripts/asc-listing.py setversion auto
.venv/bin/python scripts/asc-listing.py status
```

确认输出中的可编辑版本确为 **1.7.0** 后，上传本轮中英文说明、挂载实际 VALID 构建号，
再按审阅后的审核材料执行 `submit --yes`。审核备注应提供合成尽调项目的有效邀请码及入口说明；
不得写入真实客户信息。新功能涉及上传文档，提交前核对当前隐私申报是否覆盖实际数据处理。

## Android 命令与边界

主任务合并版本提交后，可从 main 触发现有签名构建；版本直接读取已提交的配置：

```bash
gh workflow run android-release.yml --repo AI-WorkDeck/aiworkdeck-mobile --ref main
gh run list --repo AI-WorkDeck/aiworkdeck-mobile --workflow android-release --limit 5
```

产物为 `cn-release-apk` 和 `intl-release-aab` 两份 workflow artifact，保留 30 天。
核对版本为 1.2.0 / 3、签名与总表一致后才交渠道。Google Play 当前轨道仍为草稿，
不能将上传新 AAB 等同于正式上架。国内商店认证、软著、安卓备案状态以当次后台核对为准。
