# iOS 发版前兼容检查

来源：用户 2026-10-29 要求“最主要的还是直板形态……多设备兼容要有固定的流程和方法，每次发版前自己检查一下”，dev-board #1608。

普通 iPhone 直板竖屏是主验收入口。Duo 是兼容项，不能用 Duo 通过替代直板体验；模拟器也不能替代真实相机、麦克风、折叠和系统中断验收。

## 每次候选版本的固定顺序

1. 确定候选源码提交，核对当前商店版本对应的提交及构建号。功能在 main 中不代表已经进入用户安装的版本。使用独立工作目录及合成测试资料，不在个人账号里制造测试项目。
2. 运行 `ios-auth-check` 的三组原生测试。先审阅普通 iPhone 两组的结果和实际截图，再审阅 Duo；任何一组失败、取消或缺失均不能上传。PR 检查通过后，合并提交还会再次检查，保证发布的确切源码有结果。
3. 对照下表从实际首页检查入口、点击、页面加载及返回。看截图之外，还要检查测试记录中的点击后状态。只运行组件单测、静态布局或单独页面截图不能代替完整路径。
4. 阅读三组 `ios-auth-tests-*` 结果和 `ios-auth-attachments-*` 附件，记录设备、系统版本、源码 SHA、CI 链接、通过/失败/跳过和未验证项。不能把跳过当通过，也不能用旧版本或其他设备的绿灯覆盖本次失败。
5. 有本次发版授权后才进入签名与上传。上传后按实际 IPA、ASC 构建号、审核和商店状态分别回读；不把代码合并、上传成功或构建 VALID 称为上架完成。

## 固定矩阵

| 分组 | 自动设备选择 | 必检路径 |
|---|---|---|
| `iphone`（主） | 已安装正式 iOS runtime 中可用的常规 iPhone，优先标准型号；不选 Pro Max/Plus/Duo | 默认采集首页、顶部项目/未选项目、独立录音按钮、拍照/录像、队列、头像设置、日程、助理；所有打开/关闭和返回；键盘、横竖屏往返、录音暂停/恢复/后台返回/保存 |
| `iphone-large`（主） | 同样条件下的 Pro Max/Plus；缺失时失败，不用常规尺寸顶替 | 与 `iphone` 同一套路径，检查大屏上的触达和布局；两个 iPhone 分组都执行原旋转与文件预览回归 |
| `duo`（兼容） | 支持 Duo 的正式 iOS 27.1 或以上 runtime；不得退回普通 iPhone | 同一首页入口、采集和录音、项目/队列/设置返回、双栏内容连续性；实际折叠姿态、分屏恢复另行记录 |

测试选择由 `.github/workflows/ios-auth-check.yml` 统一维护。三组共同执行 `WorkdeckTests`、登录、个人首页以及 Duo 二级页/内容连续性回归。两个普通 iPhone 分组执行完整录音、旋转、采集连续性和相关文件/键盘路径；Duo 执行录音类中五项不依赖姿态切换的路径，包含暂停音/视频、静音提醒、未归类录音返回归类和强杀恢复。录音后台返回播放一项包含实际横屏几何断言，只在普通 iPhone 执行。新增用户入口时，把“首页进入 → 首个操作 → 返回”加入相应 UI 测试，不能只在文档中打勾。

Duo 的 `XCUIDevice.orientation` 请求不能证明设备已折叠或展开。要观察实际内外屏、安全区和分屏窗口；没有对应设备/工具时，明确写“未验证”，不要伪造姿态通过。真机传感器检查前退出 Device Hub 屏幕交互，否则可能收到空画面或静音。实体来电、锁屏长录、真机配对和生产通知送达也须单列证据。

## 上传门禁

- 普通合并只触发检查，不上传。只有提交信息明确带发布标记的既有 `appstore-build` 工作流才进入发布链；其 `build-upload` 必须等待同一源码的三组兼容检查成功后才能读取签名材料。
- `fastlane ios beta`、`release`、`ci_appstore` 均先运行 `scripts/check-ios-compatibility.py`。本地要求工作目录干净，并通过已登录的 `gh` 查询当前 HEAD 最新一次 `ios-auth-check`（push 或手动 dispatch）及其当前 attempt 的三组 job；旧提交、失败、跳过、缺结果和查询失败一律停止，不回退到旧绿灯。
- PR 的 `head_sha` 与实际测试的合并引用可能不同，因此不能直接作为本地上传凭据。main 的 push 检查会覆盖真正合并提交；需要测试分支候选时，可明确 dispatch `ios-auth-check` 到该分支，然后核对源码 SHA。
- 本地先筛选当前源码的 push/dispatch，再选择最新运行及 attempt；后创建的 PR 运行不会遮挡精确源码结果。最新精确运行失败或未完成时仍停止，不回退旧绿灯。相同候选的 PR 与精确检查可并行，不因事件创建顺序额外重跑。
- CI 上传入口检查当前发布 run 的三项前置 job 结果；发布 run 仍在进行是正常的，但任何前置 job 未成功都不能继续。工具链与实际 IPA 的现有发行版检查继续保留。
- `build_local_ipa` 仍可用于纯构建验证，不会连接 ASC 或上传；不能把其成功当作发版验收。没有关闭兼容门禁的环境开关。

手动检查当前候选是否具备上传条件（只读）：

```sh
python3 scripts/check-ios-compatibility.py
```

检查脚本与 lane 的单元回归：

```sh
python3 -m unittest discover -s scripts/tests -p 'test_ios_*.py' -v
ruby fastlane/tests/local_signing_test.rb
```

## 本次实现的证据边界

门禁和设备选择的本地自动测试覆盖失败、取消、跳过、缺组、错误提交、错误工作流、PR 合并引用、过期绿灯、重跑 attempt、脏目录，以及三个上传 lane 在门禁失败时不得读取上传凭据或签名。三组原生界面是否通过以本次整合提交的 CI 和结果包为准；本文本身不宣称真机或商店版已经验收。
